# SONIC 0.2-second responsive prefix (5 source intervals)

Date: 2026-07-21
Milestone: `sonic-02-prefix`

## Goal

Add an opt-in end-to-end 0.2-second responsive SONIC prefix (5 source
intervals) so that MM state, published target rows, physics advance, and
one-prefix evidence all remain on the same horizon, while every existing
10-interval default path stays byte-for-byte equivalent in meaning.

Exactly two horizons are supported where the live MM protocol must vary:
`source_intervals` 5 and 10, with 10 the default.

- Five source intervals => 6 source boundaries => 10 target rows => 0.2 s.
- Ten source intervals  => 11 source boundaries => 20 target rows => 0.4 s.

## Design

The pipeline threads one validated `source_intervals` value from the CLI
through the C++ server, the Python schema/resample/timeline shapes, the
responsive committer, physics release, and evidence. Nothing truncates a
committed 10-step MM state.

### C++ (`sonic/cpp/mm_chunk_protocol.h`, `sonic/cpp/mm_chunk_server.cpp`)

- `mm_chunk_source_intervals_supported(n)` accepts exactly 5 or 10.
- `prepare_generate` rejects any other count with `invalid_intervals` before
  cloning the active state (no MM mutation), and generates exactly
  `request.source_intervals` steps / `source_intervals + 1` boundaries.
- The server `hello` advertises `supported_source_intervals: [5,10]`.
- The generate response reports the exact `source_intervals` and emits
  `source_intervals + 1` `timestamps_s` on the same 25 Hz grid; all step and
  boundary arrays follow the generated candidate length.

### Python schema (`sonic/python/mm_sonic/schema.py`)

- `parse_source_chunk` validates `source_intervals` into {5,10} first, then
  derives `boundary_count = n + 1` and `step_count = n` for every array shape,
  the timestamp grid, and command diagnostics. Unsupported counts fail closed.

### Resample (`sonic/python/mm_sonic/resample.py`)

- `resample_source_chunk` derives `source_boundaries`, `target_rows =
  source_intervals * 2` from the validated chunk. Five intervals produce
  exactly ten 50 Hz target rows; ten produce twenty. Right endpoints still
  recover exact binary32 source boundaries.

### Timeline (`sonic/python/mm_sonic/timeline.py`)

- `TargetChunk` derives its row count from `frame_index` and requires a
  supported target-row count (10 or 20).
- `TargetTimeline.prepare` allocates frames from the resampled row count, so a
  5-interval candidate owns frames `1..10` and `commit` advances by 10.

### Process client (`sonic/python/mm_sonic/process.py`)

- `MMChunkClient.generate` accepts `source_intervals` in {5,10} and forwards it
  to the server, rejecting anything else before contacting MM.

### Responsive committer (`sonic/python/mm_sonic/responsive_wiring.py`)

- `ManualChunkCommitter` takes a configured `source_intervals` (default 10),
  forwards it to `mm.generate`, and enforces that `steps_per_chunk ==
  source_intervals * 2`. At run time it also guards that the prepared target
  row count equals the released physics steps before any physics is released.
  This rejects the prior draft shortcut of generating/committing a longer
  target while releasing only half the physics steps (which would grow a future
  queue and make the one-prefix trace false). The generate -> validate ->
  prepare -> LAST supersession check -> publish -> mm.commit -> timeline.commit
  -> release -> record ordering is preserved.

### Manual demo (`sonic/python/mm_sonic/manual_demo.py`)

- New `--responsive-source-intervals {5,10}` (default 10) and `--mm-server`
  (default `sonic/build/mm_chunk_server`) flags.
- `_resolve_responsive_source_intervals` rejects a 5-interval request outside
  `--responsive` interactive X11 before any run bundle is created; default 10
  is always allowed.
- The responsive committer's `steps_per_chunk` is computed as
  `horizon_seconds(source_intervals) / sim_dt`, matching MM, target rows, and
  physics release on one horizon.
- The committer compares durations across the distinct rates rather than raw
  counts: five intervals at 25 Hz equal ten target rows at 50 Hz and forty
  physics steps at the live 200 Hz (`sim_dt = 0.005`) simulator rate.
- Startup preload generation uses the same selected `source_intervals`; the
  5-interval mode therefore starts with one 0.2-second queued prefix instead
  of retaining a hidden 0.4-second future queue. Terminal events and both
  manual-summary variants derive lookahead from that same prefix duration.
- Responsive evidence reports the true dynamic `source_intervals` and
  `lookahead_seconds = source_intervals / 25` (0.2 s for five, 0.4 s for ten).
- The one-prefix physical trace binding is unchanged: a committed prefix is
  presented by the next matched release; the final single queued prefix remains
  explicitly unobserved (`queued_prefixes_unobserved`).

## Live GEAR / MuJoCo result

The integrated branch was run with the official pinned GEAR binary and the
isolated MM server using `--responsive --responsive-source-intervals 5`.

Clean transaction evidence from the long-direction run:

- Run root: `/home/ubuntu/mm-sonic-responsive-r5-02-long-directions/manual-sonic/manual-20260721T023122896715Z-510858`
- 143 prefixes committed, 142 physically presented, exactly one final prefix
  queued/unobserved, and all 142 presented roots available.
- Manual summary and responsive evidence both report 0.2-second lookahead.
- Mean MM time: 1.677 ms (0.797--11.385 ms).
- Mean input-to-completed physical prefix: 1.010 s, versus 1.538 s for the
  0.4-second baseline (about 34% lower in this run).
- Mean commit-to-later-release: 0.530 s versus 0.793 s baseline.
- Mean release-to-simulation-complete: 0.464 s versus 0.724 s baseline.
- End-to-end throughput was worse: about 0.377x real time versus 0.505x for
  the baseline, showing substantial fixed cost per boundary.

The shared `DISPLAY=:1` also carried input from another active session, so the
full key stream is contaminated. Longest contiguous same-command segments are
still usable: W, S, A, and D each reached sustained positive physical
projection by approximately the sixth 0.2-second prefix and ended aligned with
the requested direction (last projections +0.111, +0.123, +0.092, and +0.109
m respectively). This proves all four directions work, but reversal settling
still takes about 1.2 simulated seconds. The result supports reducing or
pipelining fixed SONIC/physics boundary overhead next; shortening below 0.2 s
without doing that is unlikely to improve sustained response.

Generated-versus-physical projection separates the remaining bottleneck. In
the longest contiguous runs, MM-generated kinematics aligned with A and D on
the first 0.2-second prefix, S on the second, and W on the third. Physical
motion did not remain aligned until about the sixth prefix. The slow
sideways/backward response is therefore primarily tracking/dynamics after MM,
not slow vanilla-MM query or direction selection. A command-aware tracking or
reference-shaping experiment is a stronger next hypothesis than shortening
the MM prefix again.
